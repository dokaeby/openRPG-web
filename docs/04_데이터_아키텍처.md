# 04. 데이터 아키텍처

## 1. 데이터 관리 원칙

- **데이터 주도(Data-Driven)**: 게임 로직과 데이터를 분리한다. 현재는 `src/data`의 TypeScript 모듈로 관리하고, JSON 데이터 파일을 도입할 때 zod 스키마 검증을 적용한다.
- **버전 관리**: 데이터 파일은 Git으로 버전 관리
- **검증**: JSON 데이터 도입 시 로드/CI에서 스키마 검증, 오류 시 명확한 로그. 현재 TS 모듈은 타입체크(`tsc --noEmit`)로 검증한다.
- **이식성**: `core`/`data` 계층은 DOM/Three.js/브라우저 API를 import하지 않는다 (ESLint `no-restricted-imports`로 강제). Unity 전환 시 C#으로 1:1 포팅 가능하도록 유지

## 3. 데이터 로딩 방식 (웹 기준)

| 방식 | 장점 | 단점 | 용도 |
|------|------|------|------|
| 정적 JSON/TS 모듈 import | 타입 안전, 번들에 포함, 검증 용이 | 데이터 증가 시 번들 크기 증가 | 아이템, 스킬, 퀘스트 등 코어 데이터 |
| 런타임 fetch + 캐시 | 대용량 데이터 분리 로딩 | 로딩 지연, 에러 처리 필요 | 존별 몬스터/NPC 배치, 대사 데이터 |
| IndexedDB | 대용량, 구조화, 비동기 | 용량 제한(브라우저 정책), 마이그레이션 복잡 | 세이브 데이터 전용 |
| localStorage | 동기, 단순 | 5MB 제한, 구조화 불가 | 설정, 세이브 백업 |

> 권장: **코어 데이터는 TS 모듈로 번들에 포함**하고 zod로 검증한다. 런타임 fetch는 존 단위 대용량 데이터에만 사용. 세이브는 IndexedDB가 기본, localStorage는 설정/백업용.

## 4. 저장 시스템

### 4.1 세이브 데이터 구조
- 캐릭터 데이터 + 퀘스트 진행도 + 인벤토리 + 위치 + 설정
- JSON 직렬화 (IndexedDB 저장)
- 세이브 슬롯: 수동 3개 + 자동 1개
- `saveVersion` 필드 포함 (마이그레이션 대응)

### 4.2 저장소 계층

```
SaveSystem
├── IndexedDB (idb-keyval)   # 메인 세이브: 슬롯별 JSON
├── localStorage             # 설정, 그래픽 옵션, 마지막 세이브 포인터
└── Export/Import (JSON 파일) # 세이브 백업/공유 (선택)
```

### 4.3 세이브 마이그레이션
- 버전 업 시 구버전 세이브 → 신버전 변환 로직
- `saveVersion` 필드로 분기 처리, 마이그레이션 체인을 순서대로 적용
- 마이그레이션 실패 시 원본 세이브를 보존하고 에러 로그

## 5. 성능 고려사항

- **오브젝트 풀링**: 몬스터, 투사체, 이펙트 재사용
- **LOD**: 원거리 오브젝트 단순화
- **스트리밍**: 존 단위 로딩/언로딩, 오픈월드의 연속 로딩
- **데이터 캐싱**: 자주 접근하는 데이터(아이템 DB, 몬스터 DB) 메모리 캐시
- **비동기 로딩**: 씬 전환 시 로딩 화면
