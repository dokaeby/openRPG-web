# 05. 기술 스택 및 개발 로드맵 (웹 우선)

## 1. 플랫폼 전략

- **1차 플랫폼**: 웹 브라우저 (Chrome/Edge/Safari 최신 2버전)
- **렌더링**: 단순화된 3D (로우폴리 + 툰 셰이딩)
- **이후 마이그레이션**: Unity로 전환 예정. 이식성을 위해 코어 로직을 렌더링/입력/UI로부터 분리한다.

웹을 먼저 선택한 이유:
- 설치 없이 플레이어가 바로 실행할 수 있다.
- TypeScript 생태계가 빠르게 프로토타이핑하기 좋다.
- 코어 게임 로직을 순수 TS로 작성하면 Unity C#으로의 포팅 경로가 명확해진다.

## 2. 기술 스택 선택

### 2.1 렌더링 엔진 비교

| 후보 | 장점 | 단점 | 판단 |
|------|------|------|------|
| **Three.js** | 생태계/예제 풍부, 커스텀 제어 자유, glTF 표준 | 게임 전용 기능(씬 관리, GUI)은 직접 구현 | **채택** |
| Babylon.js | 게임 기능 내장(물리, GUI, 에셋 파이프라인) | 번들 크기, Three.js 대비 생태계 작음 | 차선책 |
| PlayCanvas | 엔진 완성도 높음, 에디터 제공 | 커스터마이징 제약, 인디 채용 풀 작음 | 기각 |
| 2D 엔진 (Phaser/PixiJS) | 구현 빠름, 성능 여유 | 3D 컨셉과 불일치 | 기각 |

> **채택**: Vite + TypeScript + Three.js. Babylon.js는 Three.js로 핵심 루프가 안 나오면 재검토한다.

### 2.2 전체 스택

| 영역 | 선택 | 이유 |
|------|------|------|
| 언어 | TypeScript (strict) | Unity C# 포팅 시 타입 구조가 대응됨 |
| 빌드 | Vite | 빠른 HMR, 번들 최적화 |
| 렌더링 | Three.js + toon 셰이딩 커스텀 | 로우폴리 스타일에 적합 |
| UI | DOM + CSS (캔버스 위 오버레이) | 웹의 강점, 접근성/텍스트 품질 우수 |
| 상태 관리 | 자체 이벤트 버스 + 스토어 | 프레임워크 의존 최소화 (이식성) |
| 데이터 | JSON/TS 모듈 + zod 검증 | 스키마 검증, Unity 이식 시 그대로 변환 가능 |
| 저장 | IndexedDB (`idb-keyval`) + localStorage 백업 | 용량, 구조화 데이터 지원 |
| 테스트 | Vitest (로직) + Playwright (E2E, 선택) | 코어 로직 단위 테스트 |
| 배포 | 정적 호스팅 (Cloudflare Pages / Netlify / Vercel) | CDN 캐시, HTTPS 기본 |

### 2.3 폴더 구조 (계획)

```
openRPG-web/
├── docs/
├── src/
│   ├── core/          # 순수 TS 게임 로직 (렌더링 무관) ← Unity 이식 대상
│   │   ├── stats/     # 스탯, 레벨, 경험치
│   │   ├── combat/    # 전투 공식, 턴 진행
│   │   ├── quest/     # 퀘스트 상태 머신
│   │   ├── inventory/ # 아이템, 장비
│   │   ├── race/      # 종족 보정, 관계
│   │   └── save/      # 세이브 스키마, 마이그레이션
│   ├── data/          # 아이템/몬스터/퀘스트/NPC JSON + TS 타입
│   ├── engine/        # Three.js 씬, 렌더링, 에셋 로딩
│   ├── input/         # 키보드/마우스/게임패드
│   ├── ui/            # DOM 기반 HUD/메뉴 (03 문서 토큰 사용)
│   ├── world/         # 존 관리, 스폰, 날씨, 시간
│   └── main.ts
├── public/assets/     # glTF 모델, 텍스처, 오디오
└── package.json
```

### 2.4 Unity 이식 전략

| 계층 | 웹 (TypeScript) | Unity (C#) | 이식 방법 |
|------|-----------------|------------|-----------|
| `src/core/*` | 순수 TS, DOM/Three.js import 금지 | 동일 구조의 C# 클래스 | 거의 1:1 포팅. 타입/enum/인터페이스 유지 |
| `src/data/*` | JSON + zod 스키마 | ScriptableObject 또는 JSON + 검증 | 스키마를 문서(04번) 기준으로 동일하게 유지 |
| `src/engine` | Three.js | Unity 렌더링 파이프라인 | 재작성 (로직 이식 아님) |
| `src/ui` | DOM/CSS | UGUI/UI Toolkit | 재작성. 토큰 값(색/폰트)은 그대로 사용 가능 |
| `src/input` | 브라우저 이벤트 | Unity Input System | 재작성 |

규칙: `src/core`와 `src/data`에는 Three.js, DOM, 브라우저 API를 import하지 않는다. 이 규칙을 ESLint(`no-restricted-imports`)로 강제한다. 이식 비용의 80%는 core/data 이식이고, 나머지 20%는 표현 계층 재작성이다.

## 3. 시스템 아키텍처

### 3.1 전체 구조

```
Game (main.ts)
├── Core (순수 로직, 프레임 비의존)
│   ├── GameState        # 전체 상태의 단일 진실
│   ├── EventBus         # 시스템 간 느슨한 결합
│   ├── Player           # 캐릭터, 스탯, 레벨
│   ├── Combat           # 전투 해결기 (ATB)
│   ├── QuestManager     # 퀘스트 상태
│   ├── Inventory        # 아이템/장비
│   ├── SkillSystem
│   ├── RaceSystem       # 종족 보정/관계
│   └── SaveSystem       # 직렬화/로드/마이그레이션
│
├── Engine (Three.js)
│   ├── SceneManager     # 존별 씬 로딩/언로딩
│   ├── AssetLoader      # glTF/텍스처/오디오 비동기 로딩
│   ├── EntityRenderer   # 엔티티 ↔ 3D 오브젝트 매핑
│   └── CameraController
│
├── World
│   ├── ZoneManager      # 존 전환, 스트리밍
│   ├── SpawnManager     # 몬스터 스폰/리스폰
│   ├── WeatherSystem
│   ├── TimeSystem
│   └── NPCManager
│
└── UI (DOM)
    ├── Hud             # HP/MP, 스킬바, 미니맵
    ├── Menus           # 인벤토리/퀘스트/지도/제작
    ├── DialogueUI
    └── Toast/Tooltip
```

### 3.2 설계 패턴

- **이벤트 버스**: `core` 내부 시스템은 직접 참조 대신 이벤트로 통신 (`player:damaged`, `quest:completed` 등). Unity의 C# event로 자연스럽게 포팅된다.
- **GameState 단일 소스**: UI와 로직이 같은 상태를 읽는다. UI는 상태를 직접 바꾸지 않고 명령(`dispatch`)만 보낸다.
- **데이터 주도**: 04번 문서의 JSON 스키마 + zod 검증. 로드 시 스키마 검증 실패는 빌드/CI에서 걸러진다.
- **틱 기반 업데이트**: `core`는 고정 timestep(예: 30Hz) 시뮬레이션, 렌더링은 rAF와 분리. Unity의 FixedUpdate와 같은 개념이라 이식이 쉽다.

## 4. 성능 전략 (웹 기준)

- **로우폴리 + 텍스처 아틀라스**: 메시당 삼각형 수를 낮게, 재질은 MeshToonMaterial 기반 커스텀.
- **드로우콜 관리**: 머지된 정적 지오메트리, InstancedMesh로 반복 오브젝트(나무, 풀) 처리.
- **에셋 로딩**: glTF + Draco 압축, 존 단위 분할 로딩. 초기 번들은 핵심 에셋만.
- **오브젝트 풀링**: 투사체, 이펙트, 데미지 텍스트(DOM 풀).
- **프레임 예산**: 데스크탑 60fps 목표, 16.6ms 중 로직 4ms / 렌더 10ms / UI 2ms 배분.

## 5. 개발 단계별 로드맵

### Phase 0: 기획/프로토타입 (3~4주)
- [ ] GDD 확정 (현재 문서)
- [ ] Vite + TS + Three.js 프로젝트 스캐폴드
- [ ] 코어 루프 프로토타입: 이동 + 세미리얼 ATB 전투 + 레벨업
- [ ] 종족/클래스 선택 플로우 프로토타입
- [ ] 기본 HUD 목업 (DOM)

### Phase 1: MVP (8~12주)
- [ ] 1개 존(시작 마을 + 필드) 3D 환경
- [ ] 종족 2종(인간, 엘프) + 클래스 2종
- [ ] 전투/성장/퀘스트/인벤토리 시스템
- [ ] 세이브/로드 (IndexedDB)
- [ ] 기초 사운드

### Phase 2: 콘텐츠 확장 (10~16주)
- [ ] 종족 6종 완성
- [ ] 존 3~5개, 몬스터 30종+, 보스 5종
- [ ] 제작 시스템, 날씨/시간
- [ ] 사이드 퀘스트 대량 추가

### Phase 3: 폴리싱/출시 (6~10주)
- [ ] 밸런싱, UI/UX 개선, 성능 최적화
- [ ] 사운드/음악, 배포 파이프라인
- [ ] 베타 테스트

### Phase 4: Unity 전환 검토 (별도 프로젝트)
- [ ] `core`/`data` 이식 가능성 검증 (스파이크)
- [ ] Unity 프로젝트 스캐폴드, core 포팅
- [ ] 표현 계층(엔진/UI/입력) 재구현
- [ ] 웹/Unity 데이터 스키마 동기화 유지

## 6. 기술 리스크

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 웹 3D 성능 | 저사양 기기에서 프레임 저하 | 로우폴리 고정, 품질 설정 3단계, 프로파일링 |
| Unity 이식 비용 | 전환 시 재작업 | core/data 분리 규칙을 ESLint로 강제, 초기부터 C#식 설계 유지 |
| 콘텐츠 제작량 | 일정 지연 | 존 단위 제작, 데이터 주도 콘텐츠, 절차적 소품 |
| 세이브 호환성 | 업데이트 시 세이브 깨짐 | 버전 필드 + 마이그레이션 체인 |
| 브라우저 차이 | Safari/WebKit 이슈 | 표준 WebGL2만 사용, 자동화 테스트로 주요 브라우저 확인 |
